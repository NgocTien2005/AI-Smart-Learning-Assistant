## Complexity and risks

Deployment compatibility refinement after primary-source review: Prisma CLI TLS parameters differ from the pg runtime. prisma.config.ts accepts optional MIGRATION_DATABASE_URL, defaulting to existing DATABASE_URL. Hosted runtime uses sslmode=verify-full (optional sslrootcert); CLI uses same verified session-pooler target with sslmode=require&sslaccept=strict (optional sslcert). No invalid-certificate bypass; no schema change. Guide/admin setup covers both; validate/generate and isolated migration startup verify compatibility. Official Prisma PostgreSQL connector and SSL guide plus installed pg-connection-string parser support this split.

Provide backend/scripts/bootstrap-free-admin.mjs with pure utils/freeDeployTarget.js guard/tests, wrapping the existing create-admin command. Require explicit NEW_EMPTY_PROJECT confirmation, exact project/pooler5432/database/strict TLS and empty User table; no credentials read from existing local env. This avoids fragile inline PowerShell quoting and paid Render shell, never auto-runs at startup. --check-only validates shape without database contact.

scripts/ci/common.mjs test environment explicitly clears new remote credentials/migration URL and selects local storage/SMTP so inherited developer provider settings cannot enable external requests during unit checks.
No new schema/key mapping table or client SDK. Two stores supported, no transparent migration. Metadata check cannot prevent external bucket admin changing privacy between requests; operator access/policies are a release gate. Cleanup best effort can retain orphans, no broad cleanup script. Old local documents cannot survive moving only DB to new host. Remote contract tests do not prove live provider config, mail acceptance/delivery, billing or hosted deploy. Actual external acceptance stays open task.
